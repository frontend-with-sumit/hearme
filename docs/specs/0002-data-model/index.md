# 0002. Data model

**Date**: 2026-11-15
**Status**: In Progress

## Summary

This decides the full database schema for HearMe: every table, field, and relationship the product needs for its whole current scope, not just the first booking flow. It builds directly on spec 0001 (Postgres via Prisma on Neon, app level encryption for personal data). The goal is that no later feature (admin login, pricing, availability hours, cancellation policy) needs a schema change that breaks what came before; everything it will eventually need already has a properly shaped table.

## Requirements

**User stories**:
- As the engineer building every later feature, I want every entity this product will need already migrated with the right shape, so that no feature's build requires a breaking schema change.
- As the listener (the product's one admin user), I want my clients' personal data encrypted at rest per field, so that a database breach alone exposes nothing readable.
- As a client, I want my booking to be impossible to double book and my deleted details to actually disappear from what admin can see, while the record of what happened stays for the business's own history.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
- **AC-1**: Every entity in the confirmed data model (Booking, SessionType, Payment, Refund, WebhookEvent, GoogleConnection, EmailLog, AuditLog, AdminUser, AdminSession, PasskeyCredential, AvailabilitySettings, CancellationPolicy) exists as a migrated Prisma model with the fields, types, and relationships in `## Feature design`, and `prisma generate` produces working TypeScript types with no `any`.
- **AC-2**: `Booking.timeRange` and `Booking.blockedRange` are `tstzrange` columns (`Unsupported("tstzrange")` in Prisma), and a Postgres `EXCLUDE USING gist` constraint (via `btree_gist`) on `blockedRange` rejects any new `HELD` or `CONFIRMED` booking whose buffer-padded range overlaps an existing `HELD` or `CONFIRMED` booking's `blockedRange`, applied in a hand written SQL migration. Booking creation and reschedule run inside a `SERIALIZABLE` transaction (via `$queryRaw`/TypedSQL, since Prisma Client cannot write an `Unsupported` column through its normal query builder).
- **AC-3**: Every field holding client personal data or a third party secret (`Booking.clientName`, `clientEmail`, `clientPhone`, `note`, `GoogleConnection.refreshToken`, `AdminUser.totpSecret`) is stored as a `jsonb` envelope `{v, kekVersion, wrappedDek, iv, authTag, ciphertext}`, encrypted with AAD (additional authenticated data) bound to `bookingId` (or the owning record's id) plus the field name, so a ciphertext can never be swapped between records or fields, and is never queryable by its plaintext value.
- **AC-4**: An admin can look up a booking by a client's exact email without decrypting every row, via `Booking.emailLookupHmac` (an HMAC of the email, keyed by `HMAC_KEY_Vn`, indexed).
- **AC-5**: A webhook delivery retried by Razorpay or Google is rejected at the database level, not reprocessed: `WebhookEvent` has a unique constraint on `(provider, providerEventId)`, and its stored `payload` has every personal field (name, email, phone) stripped before it is written, keeping only ids, amounts, and status.
- **AC-6**: `Booking.status` only ever holds one of `HELD`, `CONFIRMED`, `CANCELLED`, `COMPLETED`, `EXPIRED` (a Prisma/Postgres enum), and the application layer is the sole place that moves it between states (no direct writes elsewhere).
- **AC-7**: Erasing a booking's contact details (client "delete my details", or the automatic 90 day retention job) sets `erasedAt` and nulls `clientName`, `clientEmail`, `clientPhone`, and `emailLookupHmac`. Erasing the note (automatic 7 day retention job, which fires earlier and independently) sets `noteErasedAt` and nulls `note` only. Either erasure leaves `status`, all timestamps, and every related `Payment`/`Refund`/`EmailLog` row intact and queryable.
- **AC-8**: `Payment.idempotencyKey`, `Refund.idempotencyKey`, and `EmailLog.idempotencyKey` each carry a unique constraint, so a retried create call can never duplicate the operation; `Payment.razorpayOrderId` and `razorpayPaymentId` also carry unique constraints, since the webhook handler looks payments up by them. `EmailLog.idempotencyKey` is derived from `bookingId` + `emailType` + `rescheduleCount`, so rescheduling a booking does not suppress its reminder as a false duplicate of the pre-reschedule one.
- **AC-9**: Adding a new session type/price, editing the cancellation policy, or changing weekly availability hours never requires a schema migration; each is a row write against an existing table (`SessionType`, `CancellationPolicy`, `AvailabilitySettings`). A `Booking` always records which `CancellationPolicy` row applied to it via `cancellationPolicyId`, captured at hold time, so a later policy edit never changes what an existing booking is judged against.
- **AC-10**: Every timestamp column is `timestamptz`, matching spec 0001's UTC-everywhere rule.
- **AC-11**: A booking creation or reschedule attempt that hits Postgres error `23P01` (exclusion violation) or `40001` (serialization failure, possible because the transaction runs at `SERIALIZABLE`) is caught by the application layer; `40001` is retried up to 3 times with no backoff before falling through to the same "slot taken" response as `23P01`. `AvailabilitySettings.maxPerDay` is enforced in the application layer only; the database does not enforce it.
- **AC-12**: `Booking.joinToken` is a unique, non-guessable token generated once at booking creation (not derived from the booking id itself), so the stable `/j/<token>` link always resolves to the same booking without exposing the id.
- **AC-13**: `AdminUser` supports multiple WebAuthn passkeys via `PasskeyCredential`, replay protected TOTP via `AdminUser.totpLastUsedStep`, and "sign out everywhere" plus an active sessions list via `AdminSession.revokedAt`/`userAgent`/`ipHash`.
- **AC-14**: `AuditLog.metadata` never contains client personal data (enforced by a lint/review rule and named explicitly in `## Feature design`, since `AuditLog` is append only and kept forever). The database role the application connects with has no `UPDATE`/`DELETE` grant on `AuditLog`, so even a bug cannot alter or remove an audit row.

## Decision

**Chosen option**: Option 1: Model the full foundation now.

Migrate the complete schema below in one foundation migration: every entity the current scope will need, per-field envelope encryption for personal data and secrets, a database level exclusion constraint for no double booking (buffer aware), and append only, DB-hardened audit logging.

**Implementation skills**: `prisma-client-api` (`prisma/skills`, `.agents/skills/prisma-client-api/`) · `prisma-cli` (`prisma/skills`, `.agents/skills/prisma-cli/`) · `prisma-driver-adapter-implementation` (`prisma/skills`, `.agents/skills/prisma-driver-adapter-implementation/`)

Every encrypted field (`Booking.clientName/clientEmail/clientPhone/note`, `GoogleConnection.refreshToken`, `AdminUser.totpSecret`) uses the same envelope shape: `{v: int, kekVersion: string, wrappedDek: string, iv: string, authTag: string, ciphertext: string}` stored as `jsonb`. `v` is the envelope format version (lets the format itself evolve); `kekVersion` names which KEK (spec 0001's keyring) wrapped this field's DEK; `wrappedDek` is that field's own data encryption key, wrapped by the named KEK version. Encryption binds AAD (additional authenticated data) to the owning record's id plus the field name, so a ciphertext decrypted successfully can only ever be the value for that exact record and field; this is what makes "swap two ciphertexts between records" fail decryption rather than silently succeed. Erasing a field means deleting its envelope's `wrappedDek` and nulling the column: since the DEK lives in the same row being nulled, per-field envelopes (rather than one shared DEK per booking) only matter because `clientName`/`clientEmail`/`clientPhone` are erased together (contact details, 90 days) while `note` is erased separately and earlier (7 days, see AC-7); a single shared DEK across all four fields could not support that split. `Booking.emailLookupHmac` is a separate plain string column (not part of the envelope), computed as `HMAC(email, HMAC_KEY_Vn)`, so admin search never needs to decrypt every row.

**State transitions** (Booking):
`HELD` → `CONFIRMED` (webhook verified payment) · `HELD` → `EXPIRED` (hold timer elapses unpaid) · `CONFIRMED` → `COMPLETED` (session time passes) · `HELD`/`CONFIRMED` → `CANCELLED` (client, admin, or system cancels; `cancelledBy` records which). A reschedule keeps the same `Booking` row: it sets `previousTimeRange` to the current `timeRange`, writes the new `timeRange`/`blockedRange`, and increments `rescheduleCount` (so an in-flight reminder keyed to the old schedule is treated as a new idempotency target, see AC-8). No status transition leaves a terminal state (`CANCELLED`, `COMPLETED`, `EXPIRED`); erasure (`erasedAt`, `noteErasedAt`) is orthogonal to `status` and can apply from any state.

**API surface**:

This spec defines no HTTP endpoints or server actions; it is the schema and the Prisma Client that every later feature spec's API surface reads and writes. Two data-layer "surfaces" worth naming here: the shared encryption envelope helper (encrypt/decrypt a field, compute `emailLookupHmac`, wrap/unwrap a DEK by KEK version, apply the AAD binding), and the booking create/reschedule function (runs the `SERIALIZABLE` transaction via raw SQL/TypedSQL, since Prisma Client cannot write the `Unsupported("tstzrange")` columns through its normal query builder, and retries `40001` per AC-11). Both live in the shared layer per `AGENTS.md`; their own interfaces are designed when they're implemented, not here.

**Value sourcing** (every value a later action produces, computes, or displays, traced to its source in this schema):
| Action | Value produced / displayed | Source |
|---|---|---|
| Create a booking hold | `Booking.priceInPaise`, `gstRatePercent` | Copied from the chosen `SessionType` row at hold time (a snapshot; never recomputed from a later-changed `SessionType`) |
| Create a booking hold | `Booking.blockedRange` | Computed as `timeRange` padded by `AvailabilitySettings.bufferMinutes` as read at hold time, then stored (not recomputed later, so a later buffer change never invalidates an existing hold's exclusion) |
| Create a booking hold | `Booking.cancellationPolicyId` | The `CancellationPolicy` row whose `effectiveFrom` is the latest one at or before `now()`, captured once at hold time |
| Admin searches Appointments by email | The row(s) to return | `Booking.emailLookupHmac`, computed from the input email with `HMAC_KEY_Vn` at query time, matched exactly against the stored column |
| Daily retention job (contact details, 90 days) | The due-for-deletion date | Computed at run time from `upper(Booking.timeRange)` (for `CONFIRMED`/`COMPLETED`/`CANCELLED` rows) or `Booking.holdExpiresAt` (for `EXPIRED` rows) plus the fixed 90 day rule (scope item 17); never a stored `expiresAt` column |
| Daily retention job (note, 7 days) | The due-for-deletion date | Same source as above, plus the fixed 7 day rule; runs and erases independently of the contact details job |
| Confirm a booking | `Booking.consentVersion` | The active legal content version string at the moment of booking (defined in the scope item 6 spec, not this one; this spec only reserves the column) |
| KEK rotation job | Which records still need re-wrapping | `kekVersion` inside each encrypted envelope, compared against the current KEK version in the keyring (spec 0001) |
| Judge a cancellation's refund consequence | Which policy rules apply | `Booking.cancellationPolicyId`, resolved at hold time; never the currently-latest `CancellationPolicy` row |
| Render the `/j/<token>` join page | Which booking to show | `Booking.joinToken`, looked up directly (opaque, not derived from `bookingId`) |
| Validate a manage/reschedule link | Whether the link is still valid | The signed link embeds `bookingId` + `manageTokenVersion` at issue time; valid only if it still matches the booking's current `manageTokenVersion` (incrementing the column invalidates every previously issued link) |

**Key invariants**:
- No two `Booking` rows in `HELD` or `CONFIRMED` status may have overlapping `blockedRange` (enforced by the Postgres exclusion constraint, AC-2); `blockedRange` already includes the buffer, so this also prevents two bookings landing within `bufferMinutes` of each other.
- `Booking.status` only moves through the transitions listed above; the application layer is the only writer of this column.
- A `WebhookEvent` row is never written twice for the same `(provider, providerEventId)` pair (AC-5), and its stored `payload` never carries a client's name, email, or phone.
- `Payment.idempotencyKey`, `Refund.idempotencyKey`, `EmailLog.idempotencyKey` are each globally unique (AC-8), as are `Payment.razorpayOrderId`/`razorpayPaymentId`.
- `Booking.erasedAt` and `Booking.noteErasedAt` are independent: either may be set while the other is null, since contact details and the note are retained on different timers (AC-7).
- `AuditLog` rows are never updated or deleted, enforced both by the application layer and by revoking `UPDATE`/`DELETE` on the table from the database role the application connects with (AC-14).
- `AuditLog.metadata` never contains client personal data; this is a hard rule since the table is kept forever with no retention timer.
- Every encrypted field's `kekVersion` always names a KEK version that exists in the current keyring (or did, at write time); the rotation job is the only process that rewrites `wrappedDek`/`ciphertext` to a newer `kekVersion`.

**Security model**:
- This schema holds client personal data (DPDP, India) and payment references; every encrypted field above is unreadable without the KEK, per spec 0001's envelope, and bound by AAD to its exact record and field so ciphertexts cannot be swapped.
- Role based access (`AdminUser.role`: `OWNER`/`ASSISTANT`) is enforced entirely in the application layer, not via Postgres row level security: this project has exactly one query path (the Next.js app's Prisma client), so an app layer check at the repository/service boundary is the single, sufficient enforcement point. `ASSISTANT` must never be able to read `Booking.note` or create a `Refund`; `Booking.note` decryption is routed through one shared function that requires an `OWNER` principal argument, so no call site can bypass the check by calling the envelope helper directly.
- Every mutation this schema enables that touches money, access, or compliance scope (a `Refund`, an `AdminSession` login, a `Booking.note`/`clientPhone` reveal, a `CancellationPolicy`/`SessionType` change, an export, a Google connect/disconnect, a booking erasure) must write an `AuditLog` row; this is not optional (per the compliance scope named above).
- `AuditLog` is append only and kept forever, hardened at the database level (`REVOKE UPDATE, DELETE` from the app's connection role) in addition to the application layer; no retention timer applies to it, unlike the client PII fields it may reference by `targetId`.

**Configuration required**:
- No new environment variables beyond those already named in spec 0001 (`KEK_V1`/`KEK_V2`/…, `HMAC_KEY_V1`/…, `DATABASE_URL`, `DIRECT_URL`); this spec defines how those keys are used, not new secrets.

**Critical test scenarios** (each maps to an acceptance criterion in `## Requirements`):
- Happy path: two concurrent booking attempts for time ranges within `bufferMinutes` of each other; the second is rejected by the `blockedRange` exclusion constraint while the first succeeds, verifies **AC-2**.
- Failure case: a booking creation hits `40001` (serialization failure) under contention; the app retries up to 3 times and the booking still succeeds without a duplicate row, verifies **AC-11**.
- Failure case: the same Razorpay webhook event id is delivered twice; the second write is rejected by the unique constraint, not reprocessed, and the stored payload carries no client PII, verifies **AC-5**.
- Erasure: the 7 day note job runs on a `COMPLETED` booking before the 90 day contact details job does; `note` becomes null and `noteErasedAt` is set while `clientName`/`clientEmail`/`clientPhone`/`emailLookupHmac` remain intact until their own job runs later, and the row, its `Payment`, and its `EmailLog` rows stay queryable throughout for History, verifies **AC-7**.
- Reschedule: moving a `CONFIRMED` booking sets `previousTimeRange`, increments `rescheduleCount`, and a reminder already queued for the old time is not sent as a stale duplicate, verifies **AC-8**.
- Auth/permission: an `ASSISTANT` role attempts to read `Booking.note` or create a `Refund` through the service layer and is denied, verifies the security model above.

## Build plan

This is the foundation phase (per the project's Tracer Bullet build approach): unlike a feature slice, where the approach calls for the thinnest end to end thread first, the foundation itself has no later slice to thin against, since every later slice is what reads this schema. The tasks below land as one migration covering the full confirmed model, in dependency order (enums and standalone tables first, then the tables that reference them), followed by the application level pieces (the retry wrapper, the erasure functions, the seed data) a Tracer Bullet first real booking will immediately need.

1. Define all Prisma enums (`BookingStatus`, `PaymentStatus`, `RefundReason`, `RefundStatus`, `WebhookProvider`, `EmailType`, `EmailDeliveryStatus`, `AuditAction`, `AuditActorType`, `AdminRole`, `GoogleConnectionStatus`, `CalendarSyncStatus`, `CancelledBy`, `BookingOutcome`), satisfies **AC-1**, **AC-6**
2. Define the standalone/singleton models with no forward dependency: `SessionType`, `AvailabilitySettings`, `CancellationPolicy`, `GoogleConnection`, `AdminUser`, `AdminSession`, `PasskeyCredential`, satisfies **AC-1**, **AC-9**, **AC-13**
3. Define `Booking`, including the `Unsupported("tstzrange")` `timeRange` and `blockedRange` columns, the `jsonb` encrypted envelope fields, `emailLookupHmac`, `joinToken`, and `manageTokenVersion`, satisfies **AC-1**, **AC-3**, **AC-4**, **AC-6**, **AC-10**, **AC-12**
4. Define `Payment`, `Refund`, `WebhookEvent`, `EmailLog`, `AuditLog` with their foreign keys and the unique constraints from AC-5/AC-8, satisfies **AC-1**, **AC-5**, **AC-8**
5. Write the hand written SQL migration: `CREATE EXTENSION IF NOT EXISTS btree_gist`, then the `EXCLUDE USING gist` constraint on `Booking.blockedRange` scoped to `status IN ('HELD', 'CONFIRMED')`; and `REVOKE UPDATE, DELETE ON "AuditLog" FROM <app_role>`, satisfies **AC-2**, **AC-14**
6. Seed one default `SessionType` row, a default `AvailabilitySettings` row, and a default `CancellationPolicy` row with `effectiveFrom` at the time of seeding, so the app has real data to read from day one, satisfies **AC-9**
7. Implement the shared encryption envelope helper (encrypt/decrypt a field into the `{v, kekVersion, wrappedDek, iv, authTag, ciphertext}` shape with AAD bound to record id + field name, compute `emailLookupHmac`, redact personal fields before a `WebhookEvent.payload` write), in the shared layer per `AGENTS.md`, satisfies **AC-3**, **AC-4**, **AC-5**
8. Implement the booking creation/reschedule function as a `SERIALIZABLE` transaction via raw SQL/TypedSQL (catch `23P01` and `40001`, retry `40001` up to 3 times with no backoff, both fall through to "slot taken"; compute `blockedRange` from the current buffer setting; on reschedule set `previousTimeRange` and increment `rescheduleCount`), satisfies **AC-2**, **AC-11**

10. Add a migration smoke test (CI) that asserts the `blockedRange` exclusion constraint and the `AuditLog` `REVOKE` both exist after `prisma migrate deploy`, catching silent drift, satisfies **AC-2**, **AC-14**
11. Run `prisma generate` against the migrated schema and confirm the generated TypeScript client compiles with no `any`, satisfies **AC-1**

## Consequences

**Positive**:
- Every later scope item (booking flow, admin auth, availability, pricing, audit log) builds on a table that already exists in the right shape; no foundation phase feature should force a breaking migration.
- The no double booking guarantee (buffer aware) and independently timed PII retention (note vs contact details) are both correct by construction (a database constraint, and independently nullable erasure columns), not habits every new code path has to remember.
- Admin can search by email without ever decrypting a full table scan, cannot read a note or issue a refund if scoped to `ASSISTANT`, and cannot alter or delete an audit row even with a bug, since that is revoked at the database role level.

**Negative / tradeoffs**:
- Several tables (`AdminUser`, `AdminSession`, `PasskeyCredential`, `AvailabilitySettings`, `CancellationPolicy`) are migrated now but sit unused until their own feature (scope items 18, 22, 23) is built; a design mistake in one is only discovered once that feature starts writing against it.
- Thirteen entities and fourteen enums in one migration is a larger single change than a single scope item would normally carry; reviewing it carefully once is cheaper than reviewing several smaller, possibly conflicting migrations later, but it is still a bigger review than usual.
- Per-field envelope encryption (six separate encrypted columns) means six separate DEKs to track per affected row; the KEK rotation job (spec 0001 follow up) has more individual envelopes to re-wrap than a one-DEK-per-booking design would have had.
- `Booking.blockedRange` duplicates information already in `timeRange` plus the buffer setting; it has to be recomputed (not just copied) whenever a booking is created or rescheduled, and the two columns can in principle drift apart if a future code path forgets to keep them in sync.
- `AvailabilitySettings.weeklyHours`/`blockedDates` and `GoogleConnection.scopes`/`busyCalendarIds` being `jsonb`/array columns rather than normalized tables means the database cannot enforce their internal shape; a bug writing malformed JSON there is only caught by application level validation, not a schema constraint.

**Neutral**:
- `Job` and the generic `Settings` entity named in scope item 3's original wording are deliberately not part of this schema (see Rationale); if scope item 3's checklist is read literally against this spec, this is why those two names don't appear.
- The exclusion constraint (`EXCLUDE USING gist`), the `REVOKE` on `AuditLog`, and the `Unsupported("tstzrange")` columns mean Prisma Migrate alone cannot express or verify this schema; the hand written SQL migration (task 5) and its CI smoke test (task 10) must be kept in sync by hand whenever `Booking`'s schema changes near these columns.
