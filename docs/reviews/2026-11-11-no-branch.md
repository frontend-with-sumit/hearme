## Minor

### 🟡 Node runtime is not pinned, and `@types/node` is two majors behind, `package.json:18`
**Problem**: Spec 0001's Tooling row requires "the current Node LTS … pinned runtimes so local, CI and Vercel builds behave the same." The scaffold has no `engines.node`, `.nvmrc` or `.node-version`. Local Node is v26.13.0 (the current LTS), but `@types/node` is `^20`.
**Why it matters**: Vercel and GitHub Actions will each pick their own default Node, which is exactly the local/CI/Vercel drift the spec is trying to prevent. Node 20 typings also hide or misdescribe APIs that exist on the runtime you actually use.
**Suggested fix**: Add `"engines": { "node": "26.x" }` (Vercel reads it) and a `.nvmrc` with `26` for local and CI, then bump `@types/node` to `^26`.

### 🟡 Vercel function region not pinned to Mumbai, `next.config.ts` / (missing `vercel.json`)
**Problem**: The spec's DB connection row and Data residency map require Vercel functions pinned to `bom1` to match Neon `aws-ap-south-1`. Nothing in the repo pins the region.
**Why it matters**: Vercel's default region is outside India. Today this does nothing because no PII code exists. But once the first decrypting function ships, the default region would break the residency promise ("functions that decrypt it live in Mumbai"), and it would do so silently.
**Suggested fix**: Add `vercel.json` with `"regions": ["bom1"]` now, while it costs nothing, or record it as a tracked prerequisite of the first data-touching feature. Either way, make it a repo artifact rather than a dashboard setting nobody can see in review.

### 🟡 Spec says "middleware" / "Edge", but Next 16 renamed it to `proxy.ts` on the Node runtime, `docs/specs/0001-stack-architecture/index.md:30-31,37`
**Problem**: The pinned Next 16.4.6 deprecates `middleware.js` and replaces it with `proxy.js` (see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/middleware.md`). Proxy runs on the Node.js runtime by default. The spec still talks about "middleware reads the request hostname", "edge middleware for the hostname split", and "Prisma is never imported into middleware (the Edge runtime can't run it)".
**Why it matters**: Whoever builds the hostname split (admin vs public) will reach for the deprecated file convention. The Edge rationale for "never import Prisma there" is also stale. The rule is still worth keeping, because proxy runs on every request, but for a different reason.
**Suggested fix**: Have `/architect` update the spec's App topology, DB connection and Hosting rows to say `proxy.ts`, and restate the reason for keeping Prisma out of it. No scaffold change needed.

### 🟡 Scaffold-time pins the spec promises are not done yet (Prisma major in AGENTS.md, Neon in Mumbai), `AGENTS.md`
**Problem**: The spec's DB connection row says "the Prisma major version is pinned at scaffold time and recorded in `AGENTS.md`". Follow-up line 98 calls Neon project creation "the scaffold step of this feature". `AGENTS.md` contains only the auto-generated Next.js block, and Prisma is not a dependency.
**Why it matters**: The feature's done criterion ("empty scaffold boots and builds") is met. But the spec's own scaffold-time commitments are still open, so it is unclear whether feature 1 is done or whether they slipped into feature 2/3 without anyone noting it.
**Suggested fix**: Either do them as part of closing this feature, or move them explicitly into the data-model / coding-standards scope item and note that in the spec's Follow-up section. Don't leave them implied.

### 🟡 Tailwind is wired through the `@tailwindcss/turbopack` loader instead of the documented PostCSS plugin, `next.config.ts:7-14`
**Problem**: The Next 16 CSS guide (`01-app/01-getting-started/11-css.md`) installs Tailwind with `@tailwindcss/postcss` plus `postcss.config.mjs`. This scaffold uses a Turbopack `rules` entry with the `@tailwindcss/turbopack` loader and has no PostCSS config. It works: the build output contains the utilities.
**Why it matters**: Tailwind now depends on Turbopack specifically. A `next build --webpack` fallback, or any tool that expects a PostCSS config (some shadcn/ui init flows, Storybook, Vitest CSS handling), would silently get unprocessed CSS. I'm not certain this will bite, so treat it as a risk to confirm, not a known bug.
**Suggested fix**: Confirm `shadcn init` (the spec's UI choice) works with this setup when it runs. If not, or for safety, switch to the documented `@tailwindcss/postcss` path.
